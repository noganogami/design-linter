# 次の実装計画

更新日: 2026-10-01

この文書は次の開発の計画。チェック済みの現行 PoC の履歴は [実装計画とテスト戦略](implementation-plan.md) に残す。

## 現在の到達点

F# PoC は以下を実装している。

- cc-sdd の限定された英語見出し profile を読む parser と Design IR。
- Requirement ID / mapping、Component / File Plan、Boundary の記入検査。
- 明示依存の抽出と循環検出。
- 構造の semantic diff、Human Review Focus、Markdown / JSON CLI。

F# 移植後は59テストと警告をエラー扱いにしたビルドが通過。旧実装との30ケースの構造比較を含む。検証の中心は作成した fixture であり、実プロジェクトでの有効性を広く実証済みという意味ではない。

未実装: EARS の条件・応答解析、binding、要件充足の検証器、skill、AI Review、Code Graph、Git 履歴の自動取得、一般利用者向けバイナリ配布。

## 作業順序

配布検証 → 現行機能の F# 移植 → EARS モデル生成 → binding → 小さな検証器 → 状態遷移検証を基本順序とする。optional skill は手作業の binding workflow が成立した後に追加できる。高度な形式手法は必要な具体例が出てから選ぶ。

### Phase 0: F# の配布可能性を確認

- [x] SDK / target framework を選び、開発環境を固定する。
- [x] 小さな F# CLI を作り、必要なライブラリを含めて self-contained publish する。
- [x] .NET 未導入の対象環境で起動・ファイル入力・JSON 出力を確認する。
- [x] 配布サイズ、起動時間、OS 依存を測定する（[検証記録](fsharp-migration.md)）。
- [x] 対応 OS / CPU と配布方法を記録する。

完了条件: 利用者に .NET を事前導入してもらわず実行できる実物を確認できる。publish 成功だけを利用環境での動作確認と扱わない。他の対象環境が未検証なら明示する。

### Phase 1: 現行 PoC を F# へ移植

- [x] fixture・期待する判定・差分を言語非依存の受入基準として整理する。
- [x] Markdown AST、根拠位置、型付き IR を移植する。
- [x] 各 mechanical rule と semantic diff を移植する。
- [x] CLI の終了コード、JSON / Markdown、Human Review Focus を移植する。
- [x] 現行実装との比較で差を説明し、意図した改善は regression test にする。
- [x] 配布物でサンプルを実行し、README の標準手順を切り替える。

完了条件: 現行 PoC の受入条件を満たす F# CLI が動作する。未解析を PASS にしない。通常実行に Node を要求しない。移行完了前に既存実装を削除しない。

### Phase 2: 決定的な EARS モデル生成

- [ ] cc-sdd EARS profile の文法と曖昧な構文の扱いを定義する。
- [ ] Requirement ID、条件、主体、応答、原文位置を抽出する。
- [ ] 対応する複合形式を明示し、未対応部分を診断する。
- [ ] 正規化・識別子・schema / parser version を含む生成物を定義する。
- [ ] CLI からモデルと不足情報を生成できるようにする。

完了条件: 同じ入力と設定から同じモデルが得られる。生成に skill が不要。原文にない状態・時間・論理を補わない。

主要テスト: 各 EARS pattern、日本語の変数部分、複合条件、区切り文字を含む本文、曖昧な `and`、未対応文、元の行位置、空白などの扱い、繰り返し生成の一致。

### Phase 3: binding とモデルの lifecycle

- [ ] 人間が編集する語彙・binding・仮定と生成物を分離する。
- [ ] 未解決の句・対象・条件を列挙する。
- [ ] 型・参照・矛盾を検査してから検証用モデルを生成する。
- [ ] 原文・参照定義・変換ルールの変更を検出し、影響する binding を再確認対象にする。
- [ ] 要件 ID の番号変更・再利用に対する扱いを確定する。
- [ ] skill なしの作成・修正・再実行手順を文書化する。

完了条件: 一度採用した意味定義を再実行ごとに再解釈しない。古い binding を黙って適用しない。解釈の確認状態と検証結果を区別する。

主要テスト: 未解決、曖昧参照、矛盾、定義変更、要件削除・番号変更、無関係な変更、再生成時の手動定義保存、同一入力でのモデル一致。

### Phase 4: 参照・Contract・グラフ・数値検証

- [ ] 検証器共通の入出力、適用可能性、根拠、仮定を定義する。
- [ ] 要件側の property と、設計側の独立した根拠を結び付ける。
- [ ] 明示的な許可／禁止依存を検証する。
- [ ] 限定した型・schema・値域の Contract 比較を実装する。
- [ ] timeout / retry などの数値制約を単位付きで検査する。
- [ ] 未対応・情報不足を成功にしない結果 schema と CLI 契約を確定する。

完了条件: 少なくとも具体的な要件について、満たす設計、反する設計、根拠不足の設計を区別できる。検査ルールの追加だけで cc-sdd の禁止事項を増やさない。

主要テスト: 型の互換／非互換、提供／要求の向き、enum・値域の境界、単位変換、禁止 edge、仮定不足、全体 deadline の有無、根拠リンク。

### Phase 5: 有限状態モデルの検証

- [ ] 状態、初期状態、イベント、ガード、効果、不変条件の最小モデルを定義する。
- [ ] 到達可能性・禁止状態・行き止まりを検査する。
- [ ] 反例の経路を元の要件・設計箇所へ関連付ける。
- [ ] 探索の上限と打ち切りを結果に反映する。

完了条件: 小さな既知のモデルで反例を再現できる。全探索・有界探索・打ち切りを区別する。行き止まりをすべて設計違反とせず、終端状態や要件との関係を判断する。

主要テスト: 到達／非到達、正常終了と行き止まり、循環、既知の反例、探索上限、決定的な結果出力。並行性・活性の一般的な証明はこの段階の保証に含めない。

### Phase 6: optional skill

- [ ] CLI の不足情報を読み、根拠付き binding 差分を作る skill を設計する。
- [ ] 既存の意味定義を無条件に再生成しないようにする。
- [ ] 同じ CLI による検証と反例説明を支援する。
- [ ] 補完用 skill と、mechanical PASS 後の AI Review を分離する。

完了条件: skill なしでも同じ成果物・検証結果に到達できる。skill は結果を上書きしない。人間が判断すべき項目を根拠付きで提示する。

Phase 3 の後に着手可能。Phase 5 完了までは待つ必要がない。自然言語による説明の文面が変わることと、検証モデル・結果が変わることを区別する。

### 必要性が確認できてから検討

- [ ] Alloy / TLA+ / SMT solver の adapter と依存・配布管理。
- [ ] Code Conformance と静的に判断できない関係の扱い。
- [ ] 実プロジェクトの文書に基づく profile 拡張。
- [ ] Git baseline の自動取得。
- [ ] 複数 spec・履歴を扱う検索・保存基盤。

実文書への適用は、入手でき次第各 phase の fixture 改善に利用する。汎用 framework、DB、複数ランタイムの常時必須化を先行させない。

## 直近の着手点

Phase 0・1 は ARM64 の限定範囲で完了。次は Phase 2 の EARS profile 文法と決定的なモデル生成。Linux は .NET 未導入コンテナ、macOS は開発機で検証している。その他 OS / CPU と公開配布は未実施。
