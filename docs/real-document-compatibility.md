# 実文書の UNKNOWN 対応

2026-10-02。ユーザーからの実文書適用結果（UNKNOWN 267件）に基づく。実文書自体はこのリポジトリにないため、報告の表記を小さな fixture として再現した。件数の減少や実文書全体の解析成功は未確認。

## 表記揺れの修正（parserVersion 0.2.1）

| 原因 | 対応 | 保持する制約 |
|---|---|---|
| `PerfWrapper、PerfCore` を単一名として解析 | 読点を名前・要件 ID リストの区切りに追加 | 自由文を名前へ推測変換しない |
| `PlanResolver（perf_runner/plan_resolver.py）` と summary が重複 | 明確なパス注記と、summary への完全一致を条件に統合 | 括弧を一律削除しない。正式名の完全一致を優先 |

詳細の順序、ASCII / 全角括弧、inline code、契約の owner / identity、元の行位置、要件宣言の矛盾、重複定義、未対応パスをテストする。パス注記だけで file mapping を成功扱いしない。Markdown adapter と parser の修正に限定し、validation rule は変更しない。

## 見直した利用方針

主な利用経路は skill とする。CLI は非対話で実行し、起動中に入力・選択・承認を求めない。「明示」は文書または保存済み設定・binding に記録する意味であり、毎回利用者が CLI に回答する意味ではない。skill なしでも検査と未解決項目の出力まで実行でき、必要なら保存する定義を人が編集して再実行できる。すべての項目を CLI 単体で解消できることは完了条件にしない。

自然言語推論で、文書内に存在する関係の読み取りや解釈候補の整理はできる。一方、未記載の事実、矛盾した説明、複数の妥当な設計判断は推論だけでは確定しない。モデルの再現性と、解釈の正しさは別に扱う。

| 課題 | ルールで行うこと | skill が補うこと | 残す判断・不確実性 |
|---|---|---|---|
| 要件範囲 `2.1–2.9` | 同じ親・昇順・両端明記の限定構文を列挙し、全 ID を照合 | 未対応表現の意図と該当する要件を示す | 逆順・親をまたぐ範囲などは黙って補わない |
| Interfaces / Flows の自由文 | 明示参照と既知の名前を照合。曖昧なセルを原文ごと保持 | 説明か参照か、参照候補と根拠を示す | 不一致を自動で無視しない。説明という分類にも解釈の根拠が必要 |
| summary だけの依存 | 明示 edge の抽出・参照・循環検査 | 本文・Contract などから方向候補と引用箇所を示す | 呼出し・データフロー・静的依存を混同しない。根拠がなければ向きは未確定 |
| パス基準の不一致 | 保存済み path-base / alias を正規化し、衝突や未解決参照を検査 | 文書内のディレクトリ説明や File Plan から基準・対応の候補を示す | suffix 一致や候補が1件であることだけで意図を確定しない |
| ファイル省略・複数 Component の見出し | 構文が確定した表現のみ展開・照合 | 省略の解釈、分割候補、対応する定義を整理する | 存在しないファイル・Component を設計上の事実として追加しない |

範囲指定は区切り記号・canonical number・展開上限を profile で定め、存在する ID だけに黙って間引かない。これらの拡張は parser の対応表記であり、cc-sdd の新しい設計制約ではない。Components 列だけを必須にせず、Flow・Contract などへの対応も維持する。

## 補完と再検証の流れ

```text
CLI: 明示情報の抽出・検証 + 未解決項目
  → skill: 根拠箇所・候補・判断が必要な点を整理
  → 保存する補完定義の差分（binding / alias / path-base）
  → CLI: 定義の形式・参照・競合・鮮度を検査して再検証
  → skill: 確認済みの結果と、解釈に依存する結果を分けて提示
```

skill の候補は元文書を書き換える唯一の手段にせず、補助ファイルとして保存できるようにする。補助ファイルはこのツールの入力であり、cc-sdd の標準成果物ではない。根拠と出典、作成元、解釈の確認状態を保持し、以後の実行は採用済み定義を再利用する。原文・参照先・変換規則が変われば影響する定義を再確認対象にする。

ルールで一意に確定する関係は自動処理する。skill による意味解釈は、スキーマや名前の検査が通っただけで「意味も検証済み」に昇格させない。未確認の候補モデルを検査する場合は、その解釈を仮定した結果として表示し、原文だけの検査結果を上書きしない。新しい意味判断が必要な点だけを人の確認に回し、毎回すべての binding の確認を求めない。

## レビュー負荷と判定

UNKNOWN は設計不良とは限らない。少なくとも parser 未対応、意味の曖昧さ、文書の情報不足、根拠の矛盾を理由として区別する。曖昧な自由文を確定的な dangling reference と見なして FAIL にしない一方、明示参照の誤りは検査する。これは今後の変更であり、現行 parser は自由文列も名前リストとして読む。

同じ原因が多数の要件へ波及する場合は、原因・原文セル単位で集約し、影響する要件・検査・候補・根拠・必要な判断を示す。主要な Human Review Focus は最大3件、全未解決項目は詳細に保持する。候補を用意できなくても、不足する事実が何かを示す。

独立した検査は継続する。要件の対応があること、全参照が検証できたこと、設計が要件の意味を満たすことを別に表示する。不完全な依存グラフから全面的な「循環なし」は主張しない。skill は UNKNOWN の説明・補完・人への問いの整理を mechanical PASS 前にも行える。品質判断を行う独立した AI Review の gate とは区別する。

次の検証には、実文書から匿名化した traceability の数行、summary と対応する詳細 block、File Plan の関係部分が有用。今回の合成 fixture だけで、実文書固有の組み合わせまで修正済みとは扱わない。

## 0.3.0 で実装した範囲

- 同一親・昇順・最大1000件の要件範囲展開と、欠番を含めた ID 照合。
- 未解決の非 Component traceability 欄を解析上の曖昧さとして診断。明示 Component の誤参照は検査を維持。
- `reviewIssues` に原因・原文引用・影響する要件・対象・rule・判断する問いを集約。全 finding は保持。
- 非対話の `--bindings`。参照 alias と Component–既存ファイル対応のみ。保存した解釈を候補 IR に適用し、原文と別の条件付き結果を生成。
- 根拠引用・既存参照・重複／競合・fingerprint の検査。不正な定義は全件未適用、古い入力は STALE。
- 配布用 [skill](../skills/design-linter-review/SKILL.md) と [JSON 契約](../skills/design-linter-review/references/bindings.md)。CLI の起動から原文・補完後の結果を説明する手順を記述。

残る制限: 依存方向の binding、汎用 path-base、自由文を説明として分類して除外する定義、Component 自体の alias、細粒度の失効検出は未実装。鮮度は文書全体で確認するため無関係な編集でも再確認になる。`accepted` も CLI が意味を証明した状態ではなく、補完結果は常に CONDITIONAL。原文だけの判定・終了コードを無条件の成功へ格上げしない。skill の実環境での判断品質と、報告された実文書での件数減少は未検証。

検証: 84テスト通過、skill の構造検証通過、補完サンプルで原文 UNKNOWN / 条件付き PASS / 終了コード3を確認。旧 fixture の `unnamed-flow` は曖昧な Flow 参照の診断が追加される意図した変更に合わせ、期待する診断・解析状態・finding 件数のみ更新した。
