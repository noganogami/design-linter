# 要件充足の検証と再現可能なモデル生成

更新日: 2026-10-02

状態: EARS モデル生成・意味の binding・要件充足検証器は今後の設計方針。構造抽出の補助として、参照 alias / Component–ファイル対応の保存と条件付き検査、およびその optional skill は実装済み（[現行契約](../skills/design-linter-review/references/bindings.md)）。以下の汎用モデルや細粒度の失効管理は未実装。現在動く機能は [MVP 仕様](mvp-spec.md) と [parser profile](parser-profile.md) を参照。

## 目的

要件と設計要素の対応漏れの確認から、設計が受入条件を満たす根拠の検証へ進める。機械的に確認できる技術要件は CLI が検証し、人間は要件解釈、モデルの妥当性、責務境界、trade-off、リスク受容を判断する。

単なる ID coverage と要件充足は異なる。例えば retry 用 Component が存在しても、再試行時の二重請求を防げるとは限らない。条件、応答、例外、Contract、状態遷移を関連付け、要件を破る反例を検討できるようにする。

## 方針

- cc-sdd の既存ルールを source of truth とする。機能追加を理由に、要件や設計にない禁止事項を新設しない。
- parser、IR、意味の補完、モデル変換、検証器、レポートを分離する。
- ツールによるモデルやレポートの成果物生成を許容する。
- 検証処理は非対話の CLI に置く。複数のサブコマンドに分かれてもよい。起動中に入力・選択を要求せず、文書と保存済み設定・binding を入力にする。
- skill を主な利用経路として設計するが、検証エンジンの依存としては optional。同じ入力・同じモデルに対する検証結果は skill の有無で変わらない。
- skill なしでも、検証と未解決項目の出力まで完結する。人間が保存する意味定義や設定を編集して再実行できるが、すべての曖昧さを解消して PASS にすることは必須としない。
- 難しい技術要件でも、形式化できる部分は静的・決定的な検査へ渡す。
- 検証器は不明な部分を推測で確定せず UNKNOWN とする。skill は根拠付きの解釈候補を提示できるが、未記載の事実を確定しない。parser 未対応、曖昧さ、記述不足、根拠の矛盾を区別する。
- 再現性と意味の正しさは別に確認する。同じ誤ったモデルを毎回生成できても正しさの保証にはならない。
- Knowledge Graph DB、Alloy、TLA+ を初期の必須技術にしない。

## 全体の流れ

```text
requirements.md                          design.md
      ↓ EARS parser                          ↓ design parser
Requirement Model                        Design IR
      ↓ 明示的な binding                      ↓ 明示的な binding
検証する性質                              Design Model
      └──────────────┬───────────────────────┘
                仮定・制約・探索設定
                         ↓
                  モデル整合性検査
                         ↓
                 性質ごとの検証器
                         ↓
           結果・根拠・反例・未解決項目
                         ↓
                Human Review Focus
```

Requirement Model は「何が成立すべきか」、Design Model は「設計がどのように動作・保証するか」を表す。要件から期待動作を作り、それを設計の実態として自己検証してはいけない。設計側には独立した根拠を要求する。

## EARS から決定的に抽出するもの

cc-sdd の [ears-format.md](https://github.com/gotalab/cc-sdd/blob/e2a0c671aef37a482404905b409ab5c27092b25b/tools/cc-sdd/templates/shared/settings/rules/ears-format.md) は、変数部分を対象言語で記述し、`When`、`If`、`While`、`Where`、`the [system] shall` などの固定句を英語で維持する方針を定めている。

| 形式 | 抽出する構造 | 別途意味定義が必要なもの |
|---|---|---|
| When | イベント、主体、応答 | イベントの定義、応答期限 |
| While | 適用状態、主体、応答 | 状態の判定方法、開始・終了条件 |
| If | 異常条件、主体、応答 | 異常の分類・検出・回復保証 |
| Where | 機能の適用条件、主体、応答 | 構成条件の解釈。実行時状態との区別 |
| The … shall | 主体、常時適用される要求 | 性質の型、検査方法 |
| 複合形式 | 明示された条件・イベントの構文構造 | 自由文内部の論理関係 |

EARS は自然言語の構造を制約する記法であり、応答の内容を自動的に形式言語へ変えるものではない。[原著者による説明](https://alistairmavin.com/ears/)

parser の原則:

- canonical Requirement ID、原文、文書位置、構文種別、条件・主体・応答の範囲を保持する。
- 対応する文法を明示し、複数の解釈が成立する場合は一つを推測で選ばない。
- `and` を機械的に論理積へ分割しない。区切り文字が自由文内にもある場合は未解決として残す。
- `While` だけから状態遷移を作らない。`shall` を一律に時間論理の eventually へ変換しない。
- 要件にない timeout、retry 回数、状態、保存方法を補わない。
- cc-sdd の構文 profile と、後述する補助的な意味定義を区別する。

## モデルと成果物

次の名称・ファイル配置は候補であり、まだ CLI の確定したインターフェースではない。cc-sdd の追加標準成果物として扱わない。

| 成果物 | 所有・生成方法 | 内容 |
|---|---|---|
| Requirement Model | CLI が再生成 | EARS の構造、原文、位置、未解決箇所 |
| Design IR | CLI が再生成 | 明示された entity、relationship、設計上の根拠 |
| bindings / 語彙定義 | 人間が管理。skill は差分を提案可能 | 自然言語句とイベント・型・条件・動作の対応 |
| Design Model | CLI が明示定義から生成 | 設計の Contract、状態、遷移、効果 |
| 検証設定 | 人間が管理。skill は補助可能 | 仮定、対象 property、探索上限、検証器 |
| Verification Report | CLI が生成 | 判定、反例、範囲、根拠、未確認事項 |

手動管理する定義と生成物を分離する。再生成で手動定義を上書きせず、生成物の直接編集に依存しない。

### 二段階の例

原文:

```text
When 決済要求がタイムアウトした, the PaymentService shall 同じ idempotency key を使用して再試行する.
```

構造抽出の例:

```yaml
requirement: "1.2"
pattern: event-driven
subject:
  text: PaymentService
trigger:
  text: 決済要求がタイムアウトした
response:
  text: 同じ idempotency key を使用して再試行する
```

人間または skill が作成し、永続化する binding の概念例:

```yaml
requirement: "1.2"
bindings:
  subject: component:PaymentService
  trigger: event:PaymentRequestTimedOut
  response:
    action: RetryPayment
    constraints:
      - retry.idempotencyKey == original.idempotencyKey
```

この例の schema と式の表記は説明用。実装時は自由なコード実行ではなく、検査可能な型付き式として定義する。key の一致を検証しても二重請求防止全体を証明したことにはならない。外部 API の保証や副作用の順序を別途扱う。

## binding と再現性

意味の解決は次の順で行う。

1. 明示的な識別子・定義を参照解決する。
2. 登録済みの語彙と変換ルールを適用する。
3. 解決できない箇所を不足情報として出力する。
4. 人間または skill が、根拠付きの補完案を作る。
5. 採用した定義を保存し、以後は CLI の通常入力とする。

skill の実行ごとにモデル全体を作り直さない。既存 binding を変更する場合は、変更理由・根拠・差分を確認可能にする。採用済み binding があれば、再生成に skill は不要。

再現性の入力には、原文、binding、語彙、文法 profile、変換ルール、schema version を含める。ID、集合の並び、数値・単位、シリアライズを正規化し、同じ入力から同じモデルを作る。

原文や依存定義が変わった binding は再確認対象とする。Requirement ID だけで同一性を判断しない。受入条件の挿入による番号変更や削除・再利用も考慮し、古い解釈を無条件に流用しない。

解析状態、binding 解決状態、解釈の確認状態、検証結果は別々に保持する。モデルの根拠や変更検出の粒度は、実装前に小さな schema と fixture で確定する。

ルールによる抽出、skill の提案、採用済みの解釈を識別し、根拠の引用・出典・作成元・確認状態を保存する。型や参照の検査が通ったことは解釈の正しさの証明にはならない。未確認の候補で検証する場合は「この解釈を仮定した結果」と表示し、原文だけの検査結果や確認済みの結果と区別する。既存定義は変更がなければ再利用し、毎回人の再確認を求めない。

## 検証する観点

検証は要件または明示的な設計制約に適用する。全 spec へ一律に新しい必須項目を課さない。

| 観点 | 決定的に実現する方法 | 人間 / skill が補う部分 |
|---|---|---|
| 受入条件の割り当て | 条件・応答・例外と設計要素の参照を照合 | 自然言語の解釈、対応先 |
| Contract | 型、必須項目、enum、値域、エラー、事前／事後条件の比較 | 要件が必要とする保証の定義 |
| 要素間の接続 | 提供／要求 Contract、入力・出力、必要経路を照合 | どの経路が要件実現に必要か |
| 依存・所有制約 | 許可／禁止 edge、書き込み権限、所有者数を照合 | 文書にある制約の形式化 |
| 状態遷移 | 到達可能性、禁止状態、行き止まりを探索 | 状態、初期状態、イベント、ガード、効果 |
| 障害・回復 | 失敗点からの回復・補償・再開経路を検査 | 対象の障害モデル |
| Retry / idempotency | key の受け渡し、副作用・保存・再試行の順序を検査 | 重複の定義、外部保証、障害時の意味 |
| 並行実行 | 実行順序の探索と不変条件検査 | 原子性、共有状態、順序保証、探索範囲 |
| 非機能制約 | 明示的な時間・回数・容量の式を比較 | 入力値、単位、負荷、外部保証 |
| 検証可能性 | 前提・操作・期待結果・観測方法との対応確認 | 適切な観測点・期待結果の選択 |

性能の実測、実コードの動作、書かれていない障害、要件解釈の妥当性を静的検証したとは主張しない。

## 検証器の構成

共通の型付きモデルを入力とする、小さな検証器の集合にする。

1. 参照・対応検証: ID、名前、関係の集合演算。
2. 型・Contract 検証: 限定した型・schema の包含・互換性。
3. グラフ制約検証: 到達可能性、循環、許可 edge、所有関係。
4. 数値・論理制約検証: 型付き制約式と単位を評価。必要になれば solver を接続。
5. 状態遷移検証: 有限モデルを探索し、禁止状態への経路を返す。
6. 実行順序検証: 並行処理・障害を含む遷移を探索する後続機能。

各検証器は適用可能な property、必要な情報、実行結果を明示する。未対応の property を PASS にせず、未検証として返す。

### 検証例

- 時間上限: 最大3回、各 timeout 3秒、待機合計2秒なら、単純な逐次モデルの上限は11秒。10秒の要求と照合する。ただし全体 deadline、キャンセル、その他の時間が不明なら結論を限定する。
- 二重請求: 最初の請求成功 → 応答消失 → timeout → 新しい key で retry → 二度目の請求、という反例をモデル探索で得る。同一 key の外部 API 保証は仮定として記録する。

## 結果の契約

現行の mechanical status を、振る舞いの証明結果へ無条件に流用しない。検証結果の schema と CLI 終了コードは拡張時に確定する。

最低限、以下を記録する。

- 対象 Requirement ID、property、設計側の根拠位置。
- 検証器とモデルのバージョン、入力識別子。
- 仮定、探索範囲、資源上限。
- 反例、判定不能の理由、未検証の条件。
- 原文とモデルの解釈についての確認状態。

有限モデルの全状態を探索した結果と、一定の深さ・時間内で反例が見つからなかった結果を区別する。timeout や探索打ち切りは検証成功にしない。モデル内で検証できたことと、現実の設計・実装の正しさを区別する。

Human Review Focus は最大3件の主要な問いにまとめ、全 finding と反例は詳細に残す。同じ未解決箇所から波及する指摘は原因単位で集約し、原文・候補・根拠・影響する要件と検査・人が決める点を示す。独立した検査は継続する。根拠のない意味的 issue を生成しない。

## Optional skill

| 作業 | skill なし | skill あり |
|---|---|---|
| 文書抽出・構造検査 | CLI | 同じ CLI |
| 未解決の意味・binding | 人間が記述 | skill が差分候補と根拠を提示 |
| 検証実行 | CLI | 同じ CLI を実行 |
| 反例の解釈 | 人間が確認 | skill が要件・設計の言葉で説明 |
| 要件解釈・trade-off・リスク受容 | 人間が判断 | skill が判断材料を整理 |

補完用 skill と、品質判断を行う AI Review は区別する。補完は UNKNOWN の解消に使うため mechanical PASS 前にも行い得る。一方、既に定めた意味的 AI Review は mechanical checks 通過後の独立処理とし、重要指摘を最大3件に絞る。

skill は検証結果を上書きしない。外部サービスの保証や未記載の前提を確定事項として追加しない。具体的な skill パッケージより先に、保存する補完定義と非対話 CLI の入出力契約を定義する。人手でも同じ定義を編集できるようにし、skill はその契約に接続する。実文書の課題への適用は [UNKNOWN 対応方針](real-document-compatibility.md) を参照。

## 後続・対象外

- Alloy: 関係・cardinality 制約が複雑になった場合に検討。
- TLA+ / TLC: 並行性、順序、retry、安全性・活性が必要な案件に限定して検討。
- Code Conformance: 設計と AST / import / symbol graph の比較。動的 dispatch・DI は断定しない。
- Knowledge Graph DB: 複数 spec・履歴・長期 traceability の需要が出てから検討。

これらの導入は未決定。初期段階で独自の汎用 model checker や巨大な plugin framework を作らない。
